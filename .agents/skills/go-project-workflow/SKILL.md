# GO 專案工作規範

## 工作位置與範圍
- 本專案是 React/TypeScript 互動演示。按本次要求修改，不把表單配置默認擴展成真實寄信、定時任務或後端服務；清楚交代模擬與實際功能。
- 此台電腦工作副本為 `/Users/luki/Documents/GitHub/GO`；`/Users/luki/Documents/ChatGPT/TVB GO` 是舊副本，不再修改。另一台電腦允許不同路徑，以 `git remote -v` 確認連接 `lukili-design/GO`。
- 開始代碼工作時確認工作目錄、分支及未提交修改。不要自動覆蓋、清空、重設本機資料或從遠端替換整個專案。需要寫入權限時走正常授權流程。
- GitHub Desktop 與 Codex 應操作同一份代碼；預覽服務也要從該目錄啟動。`localhost` 網址相同不代表服務指向正確資料夾。

## 保留內容，精確修改
- 用戶圈選或描述的是本次修改範圍。保留未提及的字段、數據、按鈕、樣式與流程；不可用簡化重寫刪掉其他內容。
- 活動卡片的投票數量、參與人數、查看活動按鈕，以及兩種投票提交方式都是既有功能，除非用戶要求，應保留。
- 分清活動介紹、投票項簡介、候選選項介紹、活動規則。折疊或省略規則只應套用到指定字段。後續明確要求優先於之前設計，不將一次修改固化為永久限制。
- 必須辨認實際使用的元件。根目錄存在同名 `.tsx`、`types.ts`，不能只按名稱判斷；從 `src` 的 import 和呼叫關係確認後再改。
- 示例應保留既有 ID、關聯、兩種提交行為及用戶自訂資料。避免反覆新增相同示例。修改默認值不會自動更新 localStorage：只對可識別的舊示例做必要遷移，不要求用戶清空全部資料。
- Banner 同時核對原圖比例、文字安全區與顯示容器；不能只改 CSS 比例造成裁切。名稱、數量和統計必須有數據依據，不能用固定數字假裝實時計算；無法去重的跨投票人數要標明累計口徑。

## 節省讀取與驗證成本
- 先用 `rg` 定位，再讀相關段落和必要呼叫端。不要為小修改輸出整份數千行元件或全部工具說明；傳輸完整檔案時不要把全文重複輸出到對話。
- 寫局部補丁。不要把零散 UI 修改擴大成重構；只在重複邏輯實際妨礙工作時拆分。
- 驗證與改動相稱：簡單文字刪除檢查局部差異即可；型別或資料流改動跑 `npm run lint` 和相關既有測試；需打包或部署時跑 `npm run build`。通過後無新風險不重跑。
- 版面、截斷、Banner、展開收起等可見修改，要盡可能在本機實際頁面檢查。編譯通過不等於視覺驗證通過；未實際查看時不得宣稱看過。
- 長篇段落的展開按鈕以實際溢出判斷，避免僅靠字數；切換投票項目和不同寬度也應正常。

## GitHub Desktop、兩台電腦與發布
- 默認由用戶在 Desktop Commit → Push；沒有發布要求時只交付本機修改。用戶明確授權代理提交/發布時可執行，但仍須核對待提交差異和目標分支。
- 換電腦前 Commit → Push；另一台開始前 Fetch → Pull。先檢查本機改動，不要直接 pull 導致未處理的衝突。Commit 只存在本機，不能宣稱已同步。
- 發布前讀當前 `.github/workflows/deploy.yml`。若仍由 Actions 打包並部署 `dist`，提交必要源碼及新增依賴文件，不要求提交本機 `dist` 或 `node_modules`；不要未經要求修改忽略規則。
- 「已提交但網站沒變」按證據定位：本機檔案 → 提交中的完整路徑與內容 → 分支是否推送 → Actions 對應 SHA 與結果 → 線上產物。不能用同名根目錄檔案當作 `src/...` 已更新，也不能只因找到某個字串就認定整個版本正確。
- GitHub 提交成功、Actions 成功、線上驗證是不同狀態，分開表述。先核對版本，再考慮快取。
- 遇到權限、網路、額度或自動審核拒絕，報告實際錯誤與未完成步驟，遵守拒絕條件。不要猜成其他原因、繞過限制或反覆讓用戶上傳同一檔案。
