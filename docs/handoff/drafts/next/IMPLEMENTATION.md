## 2. 建議資料關係（技術要求）

| 實體 | 最少需要表達的資料與約束 |
|---|---|
| Activity | ID、名稱、介紹、規則、時間、發佈狀態、外觀及功能關聯 |
| Session | ID、活動／簽到資源關聯、名稱、報名模式、報名時間、可空名額、簽到時間、地點、分枱設定 |
| Participation | ID、活動、場次、穩定員工 ID、來源 APP／CSV、姓名部門公司電郵快照、枱座位；同活動員工唯一 |
| Invitation | 人員、場次、版本、顯示資料、私有憑證；不以郵件發送狀態代替邀請函存在狀態 |
| CheckIn | 人員場次唯一、核銷時間、操作人／裝置、結果；成功不可重複 |
| MailBatch／MailJob／MailAttempt | 批次收件人、立即／排程、預定時間、實際時間、任務狀態、模板／邀請函版本、每次嘗試及失敗原因 |
| Draw | ID、來源、來源活動場次、標題、模式、勾選規則、公開名單開關、媒體、發佈狀態 |
| Prize | ID、Draw ID、名稱、獎品、名額／座位號數量、順序 |
| DrawRound | ID、Draw／Prize／場次、輪次、狀態、版本、候選快照、開始／揭曉／確認時間、抽出的人或座位號 |
| Winner | Round ID、人員身份、獎品及座位快照、揭曉時間；可追溯到唯一輪次 |
| SessionSeatDraw | 活動＋場次＋座位號唯一；跨按枱項目共用，獨立於每人中獎限制 |
| MediaAsset | 檔案 ID、類型、大小、權限、可用位置；不把瀏覽器 blob URL 當正式資源網址 |

關鍵區分：活動名稱≠抽獎名稱≠獎項名稱；場次 ID≠場次顯示名；活動時間≠報名時間≠簽到時間≠寄信時間；邀請函存在≠郵件已寄出；揭曉≠確認下一輪。

若現有架構將簽到配置作獨立資源，可保留設計，但必須集中解析真正的活動／場次範圍；同一份名單不可因關聯複製而有兩個互不一致的版本。

## 3. 抽獎狀態與併發

建議服務端狀態：READY → DRAWING → REVEALED → ADVANCED；項目額滿才進入 COMPLETED。

1. CMS 選項目／獎項，服務端確認權限、前一輪狀態、名額及資格。
2. 開始請求附唯一操作識別；同範圍同時間只能有一個有效輪次。
3. 原子保留本輪身份／座位，防止其他抽獎項目搶到同一人或座位。隨機運算由服務端完成。
4. DRAWING 大屏只拿動畫必要資料，不提前向 APP 洩露候選中的真正得獎者。
5. CMS 揭曉時原子寫入正式結果、用掉名額、更新跨項目排除並發布事件。APP 本人結果／允許公開的名單與統計此時生效。
6. CMS 確認只標記本輪已完成展示、開啟下一輪 READY；不得再次寫入 Winner 或扣名額。
7. 斷線或重複請求返回同一輪；狀態逆序請求拒絕。沒有授權的作廢重抽功能。

按枱輪次：一次抽出的座位可能對應多個 Winner，但只消耗一個座位名額。合資格人數可以少於枱數，不把未簽到／空位算得獎者。

此處的伺服器狀態可用不同技術命名，但不得改變上述生效點。

## 4. 接口責任清單（不是固定 URL）

| 能力 | 必須檢查／返回 |
|---|---|
| 管理活動／場次／抽獎配置 | 管理權限、版本衝突、條件必填、發佈與草稿分離 |
| CSV 預檢與匯入 | 檔案欄位、逐行錯誤、身份重複、目標場次名額、實際成功數 |
| APP 報名 | 登入身份、活動可見、場次開放、服務端時間、原子容量、同活動身份唯一 |
| 調整場次／座位 | 權限、已簽到限制、容量、唯一座位、舊 QR 撤銷或版本更新、邀請函更新 |
| 本人邀請函 | 只允許本人，返回最新內容及是否可核銷；不暴露其他人的 token |
| 核銷 | 憑證、活動場次、簽到時段、單次成功、記錄操作來源 |
| 建立發送任務 | 權限、明確收件人、模板、時間、去重鍵；返回任務而非假裝已寄成功 |
| 查詢郵件任務 | 排程、成功、失敗、待重發及歷史；不可把預約當成功 |
| 開始／揭曉／確認輪次 | 僅 CMS 可寫，狀態轉移合法、可重試、同輪唯一 |
| 大屏快照／事件訂閱 | 展示授權、活動場次、序號／版本、斷線恢復；無寫入權限 |
| APP 本人結果 | 依登入身份返回；不受公開名單開關阻擋 |
| APP 公開名單 | 僅返回允許公開且已揭曉的結果；服務端過濾，不能只靠前端隱藏 |
| 活動統計 | 相同活動場次範圍，揭曉後計入，人數去重、人次可累計 |

## 5. 電郵排程要點

- 實際排程在後端運行，不依賴使用者瀏覽器或定時輪詢。
- 統一發送時間之前新增的合資格人員應加入相應初次發送批次，不能因批次建立得早而漏寄。
- 已過統一時間或沒有配置時間新增人員，由管理員點發送並在彈窗確認時間後寄出，不自動補發。
- 邀請函更新後，未發送任務應使用最新版本；已發送記錄保留原版本及時間，另標記需重發。
- 先建立耐久任務，再交寄信服務；失敗保留錯誤，不直接寫 SENT。
- 取消彈窗沒有副作用；同一提交的重送不得重複寄信。
- 自動失敗重試次數、預約取消／改期、批次衝突解決是實作設計問題，不自行添加新的產品入口；有影響時提交產品負責人確認。

## 6. 安全、時間、媒體及可用性

- 正式用戶身份來自既有身份系統，員工編號匹配規則統一；避免重建另一套帳號。
- 正式時間使用明確時區；本產品以香港時間展示，服務端使用可比較的時間值，不能依管理員電腦時間決定開放與截止。
- QR 憑證不可猜測；核銷與 APP 查看權限分開。日誌不記完整 QR token。
- 配置上傳媒體需驗證真實類型及大小，存取由正式服務提供。演示的圖片／音訊上限僅可作實作參考，不擅自把本機限制當已確認業務限制。
- 大屏重新連線恢復快照，不重新抽獎；音訊因瀏覽器限制無法播放時，不影響抽獎結果。
- 視覺驗收同時看手機窄螢幕、CMS 桌面、大屏比例；長名單與彈窗可以捲動，不能只以 TypeScript 編譯通過當完成。
- 記錄關鍵管理操作、報名、調場、核銷、寄信及抽獎輪次，便於追溯重複操作或數據爭議。

## 8. 給研發 AI 的工作指令

1. 先讀 README、PRD（或 SPEC 與 IMPLEMENTATION），再閱讀相關代碼；不從截圖或舊記錄推導相反規則。
2. 先列需求編號、既有實作及差異，再規劃修改；不要將未經確認的功能擴充包裝成必需。
3. 保留 CMS 已確認欄位及 APP 最終展示，不刪除投票等範圍外功能。
4. 移除正式運行路徑中的固定員工、指定得獎人、假寄信及本機資料真值；示例可留獨立測試環境。
5. 全部寫操作在服務端做身份、狀態與併發驗證；前端 disabled 不是業務保護。
6. 遇到需求空白先詢問，不把自己的推斷標成「已確認」。具體 API URL、技術棧及部署方案由研發按現有系統設計。
7. 每個需求附可執行測試或可重現驗收步驟；優先驗證名額、身份、核銷、開獎及寄信的重試／併發。
8. 完成報告區分「已開發」「已測試」「已接通服務」「已部署」，不能因畫面可點擊就聲稱可正式使用。
