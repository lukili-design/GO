## 一、目標、範圍與術語

### 目標

把已確認的演示體驗轉為可持久保存、跨端同步、真實報名／簽到／寄信／開獎的系統。介面以演示為視覺參考，業務邏輯以最新已確認需求為準；不得將固定員工、假發送或獨立隨機演示當成正式服務。

### 範圍

包含活動基本資料及外觀、簽到配置、CSV 名單、分枱座位、邀請函、郵件時間選擇及排程、APP 活動、CMS 抽獎、大屏展示、統計與驗收。投票只保留關聯入口，不重新定義投票規則；一般訪客、考勤、通用門禁不屬本版。

### 術語與需求效力

| 詞語 | 定義 |
|---|---|
| 活動 | APP 對外呈現的活動，包含多個場次及功能關聯 |
| 場次 | 活動內的參與與核銷範圍，各有報名及簽到時段 |
| 抽獎項目 | 一個來源活動／場次下的抽獎配置，可含多個獎項 |
| 獎項 | 有名稱、獎品、數量及順序的抽獎單位 |
| 輪次 | 一次抽一位人員或一個座位號的操作 |
| 揭曉 | 正式結果成立、同步 APP 與統計的時間點 |
| 確認結果 | 結束當輪展示並進入下一輪，不再次寫入結果 |
| 公開結果 | 控制其他用戶能看的公開得獎名單；不阻擋本人結果 |
| 已確認 | 用戶明確決定的業務規則 |
| 演示基線 | 保留現有且未被要求更改的流程；不是額外批准新功能 |
| 實作選擇／技術要求 | 相容性與可用性設計，不冒充用戶明確決策 |

優先序：用戶最新明確確認 → 本版確認規則 → 演示。發現衝突先報告。章節內「需確認」的新增設計不能由 AI 自行補完後宣稱已確認。

## 二、端到端流程

### 2.1 報名與簽到

CMS 建立活動及場次 → 選指定名單／開放報名 → 發佈 → CSV 匯入或 APP 選場次報名 → 檢查重複身份及共用名額 → 自動生成個人邀請函 → 分枱／座位更新邀請函 → 按配置發送電郵 → 現場二維碼核銷 → APP 及 CMS 同步已簽到。

開放報名允許空名單先發佈。同一員工只參加同一活動的一個場次；跨場調整由 CMS 操作，已簽到不可調場。

### 2.2 邀請函與電郵

新增參與人員 → 邀請函立即可用 → 原定寄信時間尚未到：加入統一批次 → 到時後端自動寄送。

若原定時間已過或未設定 → 不自動補發 → 管理員點發送 → 彈窗選立即／未來時間 → 確認建立任務。報名／匯入、邀請函生成與寄信是三個不同事件。

### 2.3 抽獎與大屏

CMS 選活動、場次、抽獎項目 → 開始抽獎 → 大屏動畫 → CMS 揭曉 → 結果正式成立並同步大屏、本人結果、可公開名單及統計 → CMS 確認 → 下一輪開始頁。

大屏沒有正式開獎權限。按枱一次抽一座位號，同場次不重複座位號；全場一次抽一人。配置順序控制獎項，不能自動連抽。

## 三、狀態及例外矩陣

| 對象／條件 | 顯示或操作 | 例外處理 |
|---|---|---|
| 草稿活動 | CMS 可編輯，APP 不展示 | 不可正式報名、核銷或開獎 |
| 指定名單 | CSV 匯入，不開 APP 報名 | 隱藏報名時間與名額欄位，保留已填內容 |
| 開放報名未開始／截止／額滿 | 禁止新增 APP 報名 | 服務端再次驗證；名額空值不視為 0 |
| 已報名、未分枱 | 邀請函已生成，座位待安排 | 不虛構枱座位資料 |
| 已簽到 | 顯示時間，QR 不再可核銷 | 重複掃碼不新增成功紀錄 |
| 待定時發送 | 顯示預計時間 | 不等於已寄出；失敗留原因 |
| 抽獎中 | 大屏動畫 | 刷新不重抽，未揭曉不公開結果 |
| 已揭曉、未確認 | 結果已正式成立 | 不再次抽人；確認只推進輪次 |
| 不公開名單 | 保留本人結果及中獎標識 | 公開接口不得返回其他人明細 |
| 無合資格候選 | 不開空輪次 | 提示資格不足，不擅自破例或補人 |
| 取消發送彈窗 | 無副作用 | 不建立任務、不更改成功發送時間 |

此表不新增產品狀態標籤；APP 抽獎卡片仍依最終需求移除右上角狀態及獨立模式行。

## 五、詳細功能規格與驗收案例

### 1. 角色、入口與邊界

| 編號 | 規則 |
|---|---|
| NAV-01 | APP 在「工作日常」提供「活動」入口；不增加底部活動導航。活動列表不再出現重複的「活動」標題或「全部活動／我的活動」切換。 |
| NAV-02 | CMS 提供活動管理、簽到管理、抽獎管理；各自維護配置，透過關聯資料共同服務同一個活動。 |
| NAV-03 | 大屏為展示端，正式開獎僅由 CMS 操作。演示頂部「抽獎大屏」入口位於保安門禁系統之後，並保留 CMS 抽獎列表「預覽」入口。 |
| NAV-04 | 普通用戶只能操作自己的報名、查看自己的邀請函及個人結果；CMS 管理員管理名單、配置、發送與抽獎；核銷人員只執行授權場次的簽到；大屏不具備開獎寫入權限。具體角色名沿用正式身份系統。 |

### 2. CMS 活動管理

#### ACT-01 基本資料與外觀（演示基線）

| 欄位 | 要求 | APP 用途 |
|---|---|---|
| 活動名稱 | 必填 | 列表及詳情標題 |
| 活動開始／結束時間 | 必填，結束晚於開始 | 活動時間及生命周期 |
| 活動介紹 | 保留完整內容 | 詳情超過三行收合並顯示省略號；可展開／收起 |
| 活動規則 | 保留完整內容 | 活動詳情規則區 |
| 頂部圖片、底部 Banner | 上傳、預覽、更換、移除 | 使用 CMS 圖片，不寫死盆菜宴配圖 |
| 背景漸變起始／結束色、內容底色 | 沿用配置 | 保持文字可讀；相同顏色即純色 |
| 底部連結（若有配置） | 沿用既有資料 | 點擊底部圖跳轉指定連結 |
| 活動功能與關聯 | 簽到、抽獎、投票入口按配置顯示 | 不顯示未啟用功能 |

ACT-02：保存草稿與發佈分開。草稿不出現在普通 APP 活動列表。已發佈活動按時間顯示即將開始／進行中／已結束。活動時間與報名時間、簽到時間是不同欄位，不能互相替代。

ACT-03：一個活動可有多個場次、每場多個抽獎項目。同一來源活動及場次是抽獎資格／不重複中獎的主要範圍。簽到資源的技術 ID 與 APP 活動 ID 必須透過明確關聯解析，不得按標題猜測。

ACT-04：投票保留原有關聯、卡片數據與入口，不重寫或刪除既有投票功能；完整投票規格不在本文件內。

ACT-05：開放報名設定完整即可發佈，允許沒有名單、未分枱；之後報名及分枱。不得沿用演示「必須先有參與名單與邀請函」的限制。

### 3. CMS 簽到設定與報名

#### REG-01 參與方式（已確認）

- 指定名單：只在「參與名單」透過 CSV 匯入參與人員，不開放 APP 自助報名。
- 開放報名：TVB GO APP 顯示報名入口，同時支援 CMS CSV 匯入。
- 「參與方式」下方同時顯示以上兩項說明。
- 只有開放報名顯示各場次報名開始時間、結束時間、名額。切換方式不清空已填設定。

#### REG-02 欄位

| 欄位 | 必填／條件 | 規則 |
|---|---|---|
| 活動地點 | 必填，紅色 * | APP 在各場次卡片內顯示 |
| 簽到位置 | 選填 | 空白顯示「於活動地點簽到」 |
| 參與方式 | 必選，紅色 * | 指定名單／開放報名 |
| 場次名稱 | 必填，紅色 * | 例如場次一、場次二；以 ID 關聯 |
| 報名開始／結束時間 | 開放報名必填，紅色 * | 結束晚於開始；目前演示要求報名截止不晚於簽到截止，正式沿用 |
| 場次報名名額 | 選填 | 提示「不填寫則不限制報名名額」；正式系統留空確實不限名額；有值須為正整數 |
| 簽到開放／截止時間 | 必填，紅色 * | 截止晚於開放，且不得晚於活動結束 |
| 分組方式 | 必選，紅色 * | 不分組／按組分配 |
| 組別稱呼、每組／枱人數 | 啟用分組時必填，紅色 * | 容量為正整數 |
| 分配座位號 | 分組設定選項，紅色 * | 布林選擇，否亦是有效設定，不等於強制勾選 |

REG-03：同一員工在同一活動只能參加一場。APP 重複提交不得新增第二條參與記錄；CSV 與 APP 也須檢查相同員工身份。用戶不能透過選另一場繞過限制。

REG-04：報名成功立即建立個人邀請函，APP 可查看。未分枱／座位時顯示待安排；分配完成後更新同一人的邀請函。電郵發送另按 CMS 排程，不因生成邀請函就擅自寄信。

REG-05：報名時間區間採開始含、結束不含；尚未開放、已截止、已結束、名額已滿時不能提交。時間與容量在服務端再次檢查，不只依賴按鈕 disabled。CSV、APP 報名及 CMS 調場共用同一場次上限，任何入口都不能超額。

REG-06：CMS 可在未簽到前調整場次；清除原枱號及座位，舊場次二維碼失效，產生新場次憑證。已簽到不可調場。APP 更新至新場次，已發送的人員提示待重發。不得無提示地影響已保留的抽獎結果；正式實作需對已有抽獎記錄作一致性保護。

#### CSV-01 匯入（演示基線）

簽到參與名單模板欄位依序為「員工編號、姓名、部門、公司、電郵」。公司為新增資料欄位，可留空；保留舊四欄模板相容性，舊資料公司顯示「—」。抽獎專用模板維持原四欄，勿因共用解析器變更而強迫升級。提供模板下載，處理 UTF-8 BOM、引號與逗號。檢查必填欄位、電郵格式及重複身份／電郵，錯誤提示包含行號。

簽到名單按當前場次匯入；不得把同一活動其他場次已有員工再新增一次。演示簽到匯入允許有效列成功並列出錯誤，正式回應須清楚列出成功、跳過、失敗數量。抽獎專用 CSV 上傳使用整批驗證，出錯則本次不替換舊名單。兩者不可混淆。

CSV 導入成功自動生成邀請函，未分枱時顯示待安排。未到統一寄信時間加入批次；時間已過或未配置時，由管理員透過發送時間彈窗安排寄送。

CSV-02：簽到參與名單及共用的電郵人員列表，在部門後顯示公司欄；匯入後保留公司資料，不以公司取代原身份去重規則。

#### CSV-03 參與人員欄位

| 欄位／順序 | 來源與格式 | 空值與驗證 |
|---|---|---|
| 員工編號 | CSV 或登入身份；文字 | 必填；同一活動唯一身份，不用姓名替代 |
| 姓名 | CSV 或員工資料 | 必填；顯示用，不作唯一鍵 |
| 部門 | CSV 或員工資料 | 必填；位於公司之前 |
| 公司 | 新版 CSV 第四欄 | 可留空；舊四欄模板或舊記錄顯示「—」；不改變去重範圍 |
| 電郵 | 新版 CSV 第五欄；舊模板第四欄 | 必填，驗證格式；解析器依表頭辨認，不按固定第五格讀所有檔案 |

公司欄位同時顯示於參與名單與共用的電郵邀請記錄列表。保存、調場及分枱時保留公司資料。


### 4. 分枱、座位及核銷

SEAT-01：保留人員列表與分枱概覽、自動分枱、新增／重新命名枱、刪除空枱、待分配區、按姓名／編號／電郵／部門／枱號篩選、單人及批量調整座位、交換座位。

SEAT-02：同一場次同一枱的座位號不可重複，不可超過枱容量。不同枱可有同一座位號 A；不同場次獨立分配。顯示座位號與儲存值須有一致映射，不能把字母 A 和數字 1 當不同位置。

SEAT-03：安排變更需保存，未保存不能發送邀請函。保存前可預覽變更及取消。更新邀請函內容，已發送的人員標記待重發。僅改座位不應新增參與人或遺失已簽到記錄。

CHECK-01：每張邀請函對應活動／場次／人員的個人二維碼。核銷驗證憑證歸屬、活動發佈狀態、簽到時段及是否已核銷。成功寫入唯一簽到記錄及時間。

CHECK-02：重複掃碼顯示原簽到時間，不新增第二次成功；錯誤活動／場次、失效憑證、未到時間、已截止均拒絕。並發掃碼也只能一次成功。

CHECK-03：CMS 提供應到、已簽到、未簽到、簽到率及部門／枱分布；明細可搜尋及篩選。APP 已核銷邀請函顯示「已簽到」及時間，不再展示可用入場碼；活動結束顯示失效狀態。

### 5. 邀請函與電郵

INV-01：邀請函背景圖獨立於活動 Banner；內容底色、邀請文案沿用 CMS。內容包括活動、姓名、場次、簽到時間、活動地點、簽到位置、已配置的枱／座位及個人二維碼。未分組不顯示枱座位空欄。

INV-02：APP 未報名／未獲邀時文案為「報名或獲邀後，可在這裡查看您的個人邀請函。」；已報名立即可看邀請函（REG-04），已簽到與已結束使用對應狀態。不得以是否寄過電郵作為查看邀請函的唯一門檻。

MAIL-01：電郵直接展示個人電子邀請函圖片，取消「查看電子邀請函」跳轉按鈕。電郵正文保持簡短，不重複圖片中的場次、時間、地點及枱座位欄位。圖片含可掃描二維碼，需確認常用郵件客戶端實際顯示品質。

MAIL-02：配置保留電郵主旨、正文、可選的初次發送日期時間；提供人員選擇與電郵預覽。預覽彈窗內容可上下捲動。

MAIL-03：單人發送／重發／重試及「發送/已勾選(人數)」均先開彈窗，顯示收件人數，可選立即發送或指定未來日期時間；確認後才建立任務，取消不發送。不接受空白或過去的預約時間。

MAIL-04：正式系統到時自動寄送，不依賴 CMS 頁面保持開啟。保存預約不代表已寄出；只有郵件服務確認受理／成功後才更新相應發送記錄，失敗需保留原因。

MAIL-05：發送狀態包含未發送、待定時發送、已發送、發送失敗；待重發表示內容變更後需再寄，可與歷史已發送並存。保留最近成功發送時間、預約時間、各次嘗試紀錄，支援篩選。

MAIL-09：電郵邀請記錄新增獨立「預計發送時間」欄，置於發送狀態與最近發送時間之間。優先顯示人員個別預約；沒有個別預約且尚未發送時，顯示尚未到期的統一發送時間；其餘顯示「—」。預計時間不等於已成功發送時間。

MAIL-06：發送前驗證收件人、活動／場次、可用邀請函及發送時間；重發只處理選定人員。相同確認請求重試不能多建立一次任務。新的重發是新的有意操作，與網絡重試區分。

MAIL-07：提供按狀態篩選、勾選及批量發送；本期不提供獨立「失敗／待重發一鍵重發」按鈕。

### 7. 抽獎資格與計算

DRAW-01 全場：在當前項目的合資格人員池中抽人，一輪一位；獎項數量是人數。勾選僅限已簽到則未簽到不可中獎；取消則名單內未簽到也可參與。

DRAW-02 按枱：一輪抽一個座位號，所有已選枱上該座位的合資格人員獲得當前獎品。數量指要抽幾個座位號，不是人數。例如 A → 各枱 A 座位獲獎，再抽 C → 各枱 C 座位獲下一獎項。

DRAW-03：同一來源活動及場次內，按枱抽出的座位號永不重複，跨獎項、跨按枱項目共用排除記錄；下一場次可重新使用 A。此規則獨立於「每人僅可中獎一次」勾選項，取消勾選也不能重抽同場 A。

DRAW-04：按枱抽中 A 時，勾選簽到限制則只讓已簽到的 A 獲獎；未勾選則 A 未簽到也可獲獎。空座位或不合資格者不產生虛構得獎人；候選座位至少要有一位合資格人員，避免空抽。

DRAW-05：勾選每人僅可中獎一次時，在相同來源活動及場次，先按枱得獎者不得再中全場獎，也不得在其他獎項再中。其他活動、其他場次不受此範圍限制。取消時可跨不同獎項得獎；同一獎項不能把同一人重複計為多個名額（演示基線）。

DRAW-06：開獎時重新確認已簽到等資格，之後保留本輪資格快照；新簽到只能影響後續尚未開始的輪次。去重按穩定員工身份，不按姓名或本次匯入行 ID。

DRAW-07：不足名額時不能偽造得獎者或突破排除規則；提示剩餘資格不足並阻止空開獎。異常處理、強制完結、作廢重抽不在已確認範圍，不自行提供。

DRAW-08：按枱需要獨立座位開獎紀錄，不能僅從中獎人員反推已抽座位；即使後續人員資料變更，已抽座位仍須保留。

### 8. CMS 開獎流程與大屏

SCREEN-01：正式大屏只顯示 CMS 當前選定的活動／場次／項目及輪次。不得在大屏本地抽隨機結果，也不得由大屏獨立保存結果。

SCREEN-02：流程為待開始 → CMS 開始抽獎 → 大屏動畫 → CMS 揭曉結果 → 大屏結果公布 → CMS 確認得獎結果 → 下一輪開始頁。揭曉即正式生效、同步 APP 及統計；確認只進入下一輪。斷線刷新必須恢復同一結果，不允許重抽。

SCREEN-03：每次確認後回到下一輪開始頁，不自動連抽。當前獎項額滿才進入下一獎項；順序由 CMS 配置。例：按枱獎品一、按枱獎品二，再由主持人選全場抽獎，按三等獎、二等獎、一等獎抽取。不同抽獎項目不擅自自動跨越。

SCREEN-04：展示有年會氣氛的背景、動畫、揭曉效果與得獎卡片。按枱突出座位號並列得獎人；全場顯示得獎人、獎項與獎品。多人結果可分頁，不能漏顯得獎者。

SCREEN-05：移除「TVB GO · ANNUAL CELEBRATION」「年會抽獎演示」、開啟音效、全螢幕及重複「查看中獎名單」按鈕。正式大屏亦移除開獎、揭曉、確認與重新示範操作；控制移至 CMS。

SCREEN-06：重新連線取得伺服器最新輪次與結果快照；舊訊息不得覆蓋新狀態。同一輪不能重複扣名額／新增結果。揭曉音效不因同一事件重送而重播。

SCREEN-07：完成所有配置獎項後顯示「本場抽獎已結束」。此處指選定抽獎項目完成，不應把整個活動強制結束。

### 9. APP 活動詳情

APP-01：列表使用 CMS 活動名稱、配圖、時間、介紹及功能入口；盆菜宴兩張示例置頂僅為演示資料，不是所有正式活動的固定排序規則。列表及詳情可在手機容器內正常上下捲動。

APP-02：頁籤為「活動詳情／我的邀請函／抽獎活動」，按功能啟用顯示。活動詳情時間盡量一行；同日省略重複日期，跨日保留兩端日期，不截掉資訊。

APP-03：活動介紹超過實際三行時收合、省略並提供展開／收起；不足三行不出現按鈕。不要對活動規則套用此折疊要求。

APP-04：活動詳情顯示場次選擇、報名動作與結果、場次安排及規則；每個場次卡片內顯示簽到時間、活動地點、簽到位置。地點不另放在頁面上方或場次外。

APP-05：報名成功顯示已選場次；邀請函依 INV-02。活動結束不再允許報名或使用二維碼入場，仍可查看允許顯示的歷史抽獎資料。

APP-06：抽獎活動可切換場次一／場次二（名稱讀 CMS），項目及公開名單按所選場次顯示。個人結果只來自本人實際參與的該場次，不複製另一場的中獎效果。

APP-07：每獎項獨立一張卡片，依次顯示「抽獎名稱 · 獎項名稱」「獎品」「得獎名額」。取消獨立模式一行，取消右上角未開始／抽獎中／已抽獎標籤，取消名額後的抽獎狀態文字。按枱名額以座位號數量表達，不能假稱固定人數。

APP-08：本人已中獎，在該獎項名稱旁顯示「中獎」標識；保留獨立「我的得獎結果」區塊。揭曉前不提前顯示姓名，也不直接判定最終未得獎。全部完成且本人無獎時顯示未得獎提示。

APP-09：下方保留「已公布得獎名單」。每個項目按 LOT-10 決定是否列入；關閉公開的項目不能在公開 API 中洩露其他人姓名。本人結果及中獎標識照常顯示。公開開關可在抽獎後調整顯示，不刪除歷史結果。新抽獎預設不公開（沿用本次演示設定）；舊資料遷移需保留既有公開選擇，不靜默翻轉。

APP-10：未開始也可看已發佈抽獎項目、獎品及名額；無可公布名單顯示「暫無已公布得獎名單，敬請期待。」。演示狀態按鈕正式版不出現。

### 10. 統計與通用介面

REPORT-01：活動總體數據按簽到／抽獎切換；抽獎篩選為場次、抽獎模式、獎項，桌面三欄一行。簽到按場次統計，抽獎顯示項目數、參與抽獎人數、中獎人數及中獎人次。

REPORT-02：「人數」按身份去重；「人次」按得獎記錄計數。一人多獎不可在中獎人數重複計算。只計已揭曉的正式結果；已揭曉但尚未按確認亦計入，未揭曉不計。

UI-01：CMS 沿用共用表單、按鈕及表格元件；返回用左箭頭＋返回，彈窗右上 X。調整場次、調整座位、交換座位保持相同操作按鈕風格。

UI-02：畫面必填星號與實際驗證一致；草稿可容納未完成設定，發佈／執行時驗證對應必要資料。不要以是否上傳大屏背景或音樂阻止發佈。

測試需同時覆蓋預約寄信、並發報名、並發核銷、並發開獎及斷線恢復；不是只驗證前端畫面。

關鍵區分：活動名稱≠抽獎名稱≠獎項名稱；場次 ID≠場次顯示名；活動時間≠報名時間≠簽到時間≠寄信時間；邀請函存在≠郵件已寄出；揭曉≠確認下一輪。

若現有架構將簽到配置作獨立資源，可保留設計，但必須集中解析真正的活動／場次範圍；同一份名單不可因關聯複製而有兩個互不一致的版本。

### 3. 抽獎狀態與併發

建議服務端狀態：READY → DRAWING → REVEALED → ADVANCED；項目額滿才進入 COMPLETED。

1. CMS 選項目／獎項，服務端確認權限、前一輪狀態、名額及資格。
2. 開始請求附唯一操作識別；同範圍同時間只能有一個有效輪次。
3. 原子保留本輪身份／座位，防止其他抽獎項目搶到同一人或座位。隨機運算由服務端完成。
4. DRAWING 大屏只拿動畫必要資料，不提前向 APP 洩露候選中的真正得獎者。
5. CMS 揭曉時原子寫入正式結果、用掉名額、更新跨項目排除並發布事件。APP 本人結果／允許公開的名單與統計此時生效。
6. CMS 確認只標記本輪已完成展示、開啟下一輪 READY；不得再次寫入 Winner 或扣名額。
7. 斷線或重複請求返回同一輪；狀態逆序請求拒絕。沒有授權的作廢重抽功能。

按枱輪次：一次抽出的座位可能對應多個 Winner，但只消耗一個座位名額。合資格人數可以少於枱數，不把未簽到／空位算得獎者。

此處的伺服器狀態可用不同技術命名，但不得改變上述生效點。

### 5. 電郵排程要點

- 實際排程在後端運行，不依賴使用者瀏覽器或定時輪詢。
- 統一發送時間之前新增的合資格人員應加入相應初次發送批次，不能因批次建立得早而漏寄。
- 已過統一時間或沒有配置時間新增人員，由管理員點發送並在彈窗確認時間後寄出，不自動補發。
- 邀請函更新後，未發送任務應使用最新版本；已發送記錄保留原版本及時間，另標記需重發。
- 先建立耐久任務，再交寄信服務；失敗保留錯誤，不直接寫 SENT。
- 取消彈窗沒有副作用；同一提交的重送不得重複寄信。
- 自動失敗重試次數、預約取消／改期、批次衝突解決是實作設計問題，不自行添加新的產品入口；有影響時提交產品負責人確認。

### 6. 安全、時間、媒體及可用性

- 正式用戶身份來自既有身份系統，員工編號匹配規則統一；避免重建另一套帳號。
- 正式時間使用明確時區；本產品以香港時間展示，服務端使用可比較的時間值，不能依管理員電腦時間決定開放與截止。
- QR 憑證不可猜測；核銷與 APP 查看權限分開。日誌不記完整 QR token。
- 配置上傳媒體需驗證真實類型及大小，存取由正式服務提供。演示的圖片／音訊上限僅可作實作參考，不擅自把本機限制當已確認業務限制。
- 大屏重新連線恢復快照，不重新抽獎；音訊因瀏覽器限制無法播放時，不影響抽獎結果。
- 視覺驗收同時看手機窄螢幕、CMS 桌面、大屏比例；長名單與彈窗可以捲動，不能只以 TypeScript 編譯通過當完成。
- 記錄關鍵管理操作、報名、調場、核銷、寄信及抽獎輪次，便於追溯重複操作或數據爭議。
